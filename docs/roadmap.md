# 项目路线图

> 从「零代码」到「能提前提醒主人蜕皮」的完整路径。
> 本文回答两个问题：**先做什么、每一步怎么算做完**。
> 产品是什么、为什么这么做，见 [product.md](product.md)；状态快照见 [handoff.md](handoff.md)。

## 一、规划原则

1. **端到端最小闭环优先**：每个阶段结束都要有一个能亲手验证的产出，不做「三个模块都写完再联调」
2. **数据是关键路径，尽早启动**：蜕皮样本的积累周期无法压缩，其他工作必须围绕它并行
3. **先能记录，再谈判断**：第一版目标是「能记录、能对比、能看到趋势」，不是高准确率
4. **知识库独立并行**：`gecko-params.md` 的核实不依赖任何代码，可以同时推进
5. **每阶段可回滚**：一次只推进一个阶段，每阶段独立提交

## 三、关键路径

```text
固件/机位就绪 ──→ 数据积累（2–3 个月）──→ 分析管线 ──→ 判定规则 ──→ 提醒
                    ↑
                这一段决定项目总时长，且无法压缩

后端服务 ──┐
           ├──→ 与数据积累并行
知识库核实 ─┘
```

**结论：数据采集一旦可以启动，就立刻启动，其余任务全部围绕它安排。**

### 3.1 一个残酷但必须说清楚的事实

| 阶段 | 蜕皮周期 | 三个月能攒到几次 |
|---|---|---|
| 幼体 | 2–3 周 | 4–6 次 |
| 成体 | 4–6 周 | 2–3 次 |

要在统计上站得住地验证「提前 3 天预警」，2–3 次样本远远不够。**所以第一版不承诺准确率是产品决策，也是数学现实。**

第一版能诚实地交付的是：稳定的每日影像、可回看的时间线、肉眼能看出的趋势曲线。判定规则放到有足够样本之后。

## 四、阶段分解

### Phase 0：定盘与工程底座

| 项 | 内容 |
|---|---|
| 目标 | 让后端项目能被创建、能运行测试、能被 lint |
| 产出 | `server/` 工程骨架、虚拟环境、依赖锁定、工具链配置 |
| 验收 | 空测试能跑、`ruff` 与 `mypy` 能对空项目出结果、`pytest` 退出码为 0 |
| 预计 | 半天 |
| 依赖 | 无（技术决策已确认） |

### Phase 1：后端最小可用

| 项 | 内容 |
|---|---|
| 目标 | 收图 → 落盘 → 入库 → 可查询，全链路可用 |
| 产出 | 上传接口、落盘、SQLite 元数据、幂等、列表与取图接口、健康检查、结构化日志、错误契约、测试 |
| 验收 | 规格第 15 节的 10 条验收全部通过 |
| 预计 | 1–2 个工作日 |
| 依赖 | Phase 0 |
| 风险 | Python 版本与依赖兼容性；不符合则按规格 ADR-04 降级数据访问实现 |

### Phase 2：数据流提前启动

| 项 | 内容 |
|---|---|
| 目标 | **不等固件，先用现有手段开始积累影像** |
| 产出 | 临时固定机位（手机 + 支架）、每日定时拍摄流程、手工蜕皮记录表 |
| 验收 | 连续 3 天，每天至少 1 张可用照片进入后端，且时间与位置基本稳定 |
| 预计 | 当天可启动 |
| 依赖 | Phase 1 的收图能力（也可先手动拷贝进目录） |
| 说明 | 这是本规划最关键的一步。手机方案是临时的，固件就绪后替换，但**不替换已积累的数据** |

> 为什么值得做：固件从零到稳定上传通常要几天到一周，而这几天的数据是白送的。更关键的是，先用手机会提前暴露真正的问题 —— 机位怎么固定、夜拍够不够亮、守宫会不会躲在看不见的角落。这些问题和固件技术无关，却会决定数据能不能用。

### Phase 3：固件最小闭环

| 项 | 内容 |
|---|---|
| 目标 | 设备自主定时拍照并上传，脱离人工 |
| 产出 | 固件工程、摄像头初始化、定时拍照、WiFi 上传、断网存 SD、红外补光控制 |
| 验收 | 拔掉人工干预，设备按周期自动上传；断网重连后补传成功；夜间照片可辨认守宫轮廓 |
| 预计 | 3–5 个工作日 |
| 依赖 | Phase 1 的接收端点 |
| 风险 | 红外补光实际效果未知；WiFi 稳定性；供电方式 |

### Phase 4：数据积累与标注（持续）

| 项 | 内容 |
|---|---|
| 目标 | 攒够可用于分析的带标注数据 |
| 产出 | 每日影像 + 蜕皮事件记录（日期、是否顺利、是否卡皮、伴随现象） |
| 验收 | 连续 14 天无断档；至少记录到 1 次完整蜕皮周期 |
| 预计 | 2 周起，持续 2–3 个月 |
| 依赖 | Phase 2 或 Phase 3 |
| 说明 | 这段期间不空等，Phase 5 的管线可以先用已有数据开发 |

### Phase 5：图像分析管线

| 项 | 内容 |
|---|---|
| 目标 | 从每日影像里提取可对比的特征序列 |
| 产出 | 预处理（对齐、亮度归一化）、体表白度、眼部浑浊度、活动量、每日特征表、趋势曲线图 |
| 验收 | 能画出至少 14 天的白度曲线；人工核对曲线上蜕皮前的上升段，肉眼可辨 |
| 预计 | 1 周 |
| 依赖 | Phase 4 有 ≥ 7 天数据即可开工，不需等满 |
| 风险 | 固定机位仍可能因箱体移动、守宫位置变化产生噪声；需要人工剔除不可用帧 |

### Phase 6：判定规则

| 项 | 内容 |
|---|---|
| 目标 | 从特征序列得出「蜕皮前期 / 正常 / 不确定」 |
| 产出 | 判定规则、阈值、回测报告（误报率、漏报率） |
| 验收 | 在有标注数据上回测，结果可复现；三个状态都有明确触发条件 |
| 预计 | 3–5 个工作日，之后随数据持续调参 |
| 依赖 | Phase 4 至少 2 次完整蜕皮周期 |
| 说明 | 样本不足时**只交付规则与回测框架，不承诺准确率** |

### Phase 7：提醒与护理清单

| 项 | 内容 |
|---|---|
| 目标 | 判定为蜕皮前期时，主动通知并给出可执行建议 |
| 产出 | 推送通道（邮件优先）、提醒文案、蜕皮期护理清单 |
| 验收 | 模拟触发后，能在手机上收到提醒，内容与知识库一致 |
| 预计 | 1–2 个工作日 |
| 风险 | 微信推送对个人开发者有资质门槛，先用邮件或 Server 酱类服务 |

### Phase 8：前端界面

| 项 | 内容 |
|---|---|
| 目标 | 让主人能看「今天什么状态」和「历史时间线」 |
| 产出 | 今日状态页、时间线页、护理清单页、提醒设置 |
| 验收 | 手机上可打开、可翻历史照片、能看到趋势曲线 |
| 预计 | 1 周 |
| 依赖 | Phase 1 接口、Phase 5 曲线 |

### Phase 9：知识库核实（并行，越早越好）

| 项 | 内容 |
|---|---|
| 目标 | 把 30+ 处 `[待核实]` 换成带来源的确定值 |
| 产出 | 填好的 `gecko-params.md`，每条带来源与可信度分级 |
| 验收 | 无 `[待核实]` 残留；已发贴吧/爬宠群求老手挑错并回收意见 |
| 预计 | 持续，可穿插在任何阶段 |
| 依赖 | 无，可立即开始 |
| 状态 | **第一轮已完成（2026-11-02）**：全部条目已换成带来源的值，并修正 8 处错误。剩余 5 项硬核实（见文档末节），都需要真实个体数据或实物验证 |

> 这一项的优先级被低估了。判断层一旦上线，它输出的每条护理建议都来自这张表。**给错护理建议比不给更危险。**
>
> 第一轮核实推翻了三件事：豹纹守宫**需要 UVB**（原表说不需要）、日常湿度应是 **30–40%** 而非 40–60%、**蜕皮频率没有任何一致来源**（中文来源跨度从 5 天到 2 个月）。最后这条直接支持了 M6 的设计：判定必须靠个体自己的历史基线，不能硬编码全局周期。

## 八、本规划明确的取舍

1. **不追求高准确率**：样本不足时只交付规则框架与回测，不交付「准确率 90%」这种话术
2. **不先做前端**：没有数据和分析，前端只是空壳
3. **不做微信推送**：先用邮件，绕开资质门槛
4. **不扩展到其他爬宠**：第一版只做干燥型地栖守宫
5. **不追求一次做全**：每个阶段结束都停下来看数据，再决定下一步
