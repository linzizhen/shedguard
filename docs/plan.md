# 项目总计划（唯一权威）

> 本文件是本项目**唯一的计划来源**。任何开发都必须先与本文件的「当前主线」对齐。
> 角色分工：本文件 = 计划与优先级；`docs/specs/` = 具体设计；`docs/handoff.md` = 状态快照；`docs/lessons.md` = 踩坑与防复发清单；`docs/roadmap.md` = **早期规划存档（已过期，不得作为开发依据）**。

---

## 0. 使用规则（最重要，先读这一节）

### 0.1 铁律

1. **计划先行**：先有计划，再有规格，最后才是代码。顺序不可颠倒。
2. **新方案 = 先重排计划**：出现新方案、新需求、新数据结论时，**第一步是改本文件**（登记变更 + 重排里程碑 + 更新当前主线），然后才允许写规格、写代码。
3. **禁止按旧计划开发**：不允许拿着过期的计划或过期的规格直接开工。发现计划与现实不符，先停下来改计划。
4. **一次只推进一个主线**：同时最多一个「进行中」的主线；其余是「待办」或「待定」。

### 0.2 新方案的标准处理流程（强制）

| 步骤 | 动作 | 产出 | 谁能做 |
|---|---|---|---|
| 1 | 在 §6 变更记录登记一行：日期 / 变更内容 / 影响哪些计划项 | 一行记录 | 我 |
| 2 | 重排 §3 里程碑、§4 当前主线，标出新增/取消/降级 | 更新后的计划 | 我 |
| 3 | 影响架构 / 接口 / 数据模型的，写或改 `docs/specs/` 里的规格，**等用户批准** | 规格文档 | 我 → 用户批准 |
| 4 | 计划与规格都定稿后，才开始写代码 | 代码 + 测试 | 我 |
| 5 | 提交前自检：本次代码是否只做「当前主线」里的事 | 提交 | 我 |

> 一句话：**没改计划，不许改代码**。哪怕是很小的新增方案，也要在 §6 留一行。

### 0.3 冲突时的优先级

用户当次指令 > 本文件 > 规格文档 > `docs/roadmap.md`（存档）。
若用户指令与本文件冲突，先执行用户指令，**并在同一轮内更新本文件**，避免计划再次过期。

### 0.4 一次迭代的收尾清单（每轮都照这个走）

一个「迭代」= 计划项从开工到合并进 `develop`。收尾时必须逐条打勾，缺一项就不算做完：

1. **计划**：§6 有变更行，§3 状态已更新，§4 当前主线指向下一项。
2. **规格**：架构级改动有 `docs/specs/` 文档，且末尾有「实现记录（偏差表 + 验收对照）」。
3. **测试**：新增/修改的代码有对应测试；`pytest` 全绿、覆盖率不低于上一轮。
4. **质量门**：`ruff check .` 与 `mypy src tests` 全绿；App 侧 `tsc --noEmit` + `eslint .` 全绿。
5. **验收**：至少一条「真东西」证据（真模型冒烟 / 真实数据 / 截图核对 / 迁移在旧库上跑通），不能只有单测。
6. **文档**：`docs/handoff.md` 状态与数字同步；对外说明（`README.md`、`server/README.md`、`app/README.md`、`.env.example`）按需更新。
7. **踩坑**：本轮犯的错已登记进 `docs/lessons.md`（现象 → 根因 → 正确做法 → 自查）。
8. **Git**：走 `feature/*` → `--no-ff` 合并进 `develop` → 推送；提交按 `feat`/`fix`/`docs` 原子拆分。

## 1. 项目现状（一句话）

shedguard 是一个爬宠蜕皮监测系统：**接入用户已有的家用摄像头**（RTSP/ONVIF）→ 定时抓拍 → 服务端判定守宫是否「正在蜕皮」→ 通过 App 推送提醒主人查看。**软件（服务端 + 模型 + App）已全部完成并通过本地验证；固件降级为算法数据采集器；尚未接真实摄像头、没有真实饲养箱数据。**（详细状态见 `docs/handoff.md`；路线决策见 `docs/market-2026-11-16.md`）

当前最新提交：`dd85af5`（2026-11-18），`develop` 为集成分支，`main` 停在 `v0.1.0` 对应的 `784c02e`。

## 2. 产品范围与硬边界（当前版）

### 2.1 做

- **接入用户已有摄像头（P30，2026-11-16 路线 C）**：用户自购的、支持 **RTSP / ONVIF** 的家用摄像头（几十到两百元），由服务端按日程拉流抓拍 → 判定 → 提醒。**我们不自研、不量产、不卖硬件**；退换货、3C/SRRC、模具、售后全部留在成品厂一侧。
- **蜕皮检测**：判定当前这一帧是「正常 / 正在蜕皮」，在状态发生跃迁（正常 → 正在蜕皮）时提醒。
- **定时抓拍 + 服务端判定**：每 30 分钟抓一张（仅白天 08:00–20:00），上传后服务端自动分析。抓拍来源有三条，按优先级：① 用户已有的 RTSP/ONVIF 摄像头（主线）；② ESP32-S3-EYE（**降级为算法数据采集器**，只用于我们自己造数据、验证模型）；③ 手机拍照（兜底，用户手动拍）。
- **App**：宠物档案、手动蜕皮日志、拍照查验、知识库、卡皮风险评估、蜕皮提醒列表与推送。
- **萌照（P25）**：每天自动挑一张近景好照片推给主人，可保存/分享；同时沉淀真实机位数据。
- **饲养箱环境控制（P28，2026-11-13 新增）**：箱内温度 / 湿度。**先监测，后控制**；执行器用成品（智能插座、温控器），闭环跑在板子上，服务器只管配置、曲线、告警。
- **二期（待数据）**：蒙白期识别（三态分类），需要 ≥150 张蒙白样本。
- **数据贡献（P29，2026-11-16 新增）**：用户**自愿**分享照片，用来补我们最缺的真实机位数据。默认只分享**裁剪后的守宫特写**，用户可另选是否附带整张原图；开关打开后每次蜕皮事件最多留 3 张，**后台自动上传到开发者的私有数据集仓库**（HuggingFace），用户不需要任何手工操作；随时可在「分享记录」里逐张撤回（连带删除远端副本）。

### 2.2 不做

| 不做 | 原因 |
|---|---|
| **蜕皮日期预测 / 提前预警** | 2026-11-11 用户决策下线：没有足够个体历史，预测不可靠。接口保留但标 Deprecated，不再开发 |
| 自动喂食 | 与「蜕皮监测」无关，成本结构不成立 |
| 整箱整机自研（结构、风道、认证） | 2026-11-13 决策：控制能力做，但**不自己造箱体与强电执行器**，用成品插座/温控器承载安规与认证 |
| 自研监控硬件 / 小批量量产 / 卖硬件 | 2026-11-16 决策（路线 C）：调研显示认证与验厂 3–6 个月、智能宠物用品退货率 3–5 倍、活物售后责任不可控；改为接入用户已有摄像头，硬件由成品厂承担 |
| 健康诊断 | 只做观察提示，不替代异宠医生 |
| 一开始覆盖所有爬宠 | 只做干燥型地栖守宫（豹纹、肥尾） |
| 端侧推理（板子上跑模型） | 2026-11-11 决策：服务端推理，板子只负责拍照上传 |
| 夜间 / 红外抓拍 | 无红外训练数据，接受「只在白天拍」 |

> 注：早期边界里写「单张照片识别蜕皮不可靠，不做」。**现改为**：单帧状态识别可以做，但它是「定时序列里的一帧」，不承诺「单张即结论」；判定仍要结合前后日状态与置信度阈值。

## 4. 当前主线与下一步

**当前主线：C 包「别瞎说话」，然后做 B 包「能装进手机」。** 2026-11-19 用户明确「硬件留到后面，因为现在还没有硬件，先把软件做通」，把主线从「等实物」改成软件三段路：A 能被打开（已完成 P33）、C 别瞎说话（判定前输入质量门 + 「看不清」结论 + 端到端旅程测试）、B 能装进手机（EAS 构建 APK + 真机自测，需用户登 Expo 账号）。2026-11-19 当晚用户第二次否掉界面（「现在的 app 做的太丑了，搭配和配色都重做」），插入 P34；**P34 已于 2026-11-25 完成**（纸感极简，14 页 + 3 组件全部重做，`7b63d56` 已合并推送）。

P32 App 视觉重做已完成（令牌 + 组件 + 全部 14 个页面迁到设计令牌，430×932 逐屏截图核对通过）；2026-11-18 做过一次仓库整理（清理 3.4 GB 工作产物，仓库降到 588 MB，详见 §6）。P30 摄像头接入层已落地（RTSP/萤石云适配器 + 定时抓拍 + 离线兜底 + 凭据加密 + App 两页）；P31 需求验证需要真摄像头与愿意试用的用户，暂时阻塞。负责人看了小红书后质疑「启动成本与不可控因素太多」，三路调研完成（`docs/market-2026-11-16.md`），拍板走 **C：成品摄像头 + 软件层**——不自研硬件、不量产，只做「拉流抓拍 + 判定 + 提醒」。

> 2026-11-16 路线已定：C。调研结论见 `docs/market-2026-11-16.md`；本决策把 P11 固件从「产品形态」降级为「算法数据采集器」，并新增 P30（摄像头接入）与 P31（20–30 个真实用户验证）。

|---|---|---|---|

| 4 | P26 偏好打分器 / P27 头部特写检测 | 否（需要 P25 用起来的数据） | ⏸ 等 P25 上线积累数据 |

**P29 已定的三个方向（2026-11-16 用户选定，含一次修正）**：①默认只分享**裁剪后的守宫特写**，用户可另选附整张原图；②**开关打开后全自动**——后台把样本上传到开发者的**私有 HuggingFace 数据集仓库**，用户不需要点任何按钮（用户第一次答复里说「先做本地导出包」，随即修正为「自动传给我们」，以最新指令为准）；③每次蜕皮事件最多 3 张，可手动加，分享记录里逐张可撤回并连带删除远端副本。

**若没有真手机**：P18/P20 无法推进，可转「数据集扩充与复核」或「App 细节打磨」，均不改变主线。

**硬件相关的两条主线仍然阻塞**：P11 固件上板联调、P12 真实数据采集（需 ESP32-S3-EYE 与饲养箱）。P13 蒙白三态与 P14 个体校准继续挂起。

**下一个要做决定的分叉点（已被 P22 数据推到台面上）**：真机数据回来后，要决定「阈值语义」——现行 `state_min_confidence` 只是 abstain 阈值（置信度不足记 unknown），按 P22 实测它不提升召回；若要用阈值换召回，需另加一条 `p(shedding) ≥ T` 判定线。该决策记在 §7。
